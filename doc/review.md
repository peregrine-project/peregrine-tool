# Review guide

This page lists, for each frontend, the middle-end and each backend of Peregrine, the files a reviewer reads to check the verification claims and the files a reviewer can skip. The files to read hold the trusted definitions: the semantics that the theorems are stated in, the statements themselves, the printers and the runtime contracts. The files to skip hold proofs, which Rocq or Lean checks.

## Trusted base common to every route

These parts are trusted for every route through Peregrine.

- Rocq's kernel and the extraction of the Rocq sources to OCaml ([theories/Extraction.v](../theories/Extraction.v), output in `src/extraction`), and the OCaml command line in [bin/](../bin/), which reads files, calls the extracted pipeline and writes its output.
- The axioms printed by `Print Assumptions`. `Print Assumptions` on base `e526773` printed, for `peregrine_untyped_fo`, `peregrine_typed_untyped_fo`, `peregrine_typed_typed_fo` and `peregrine_untyped_cakeml`, the axioms of Rocq's primitive types (`PrimInt63`, `PrimFloat`, `PrimString` and their specifications), `functional_extensionality_dep`, `proof_irrelevance` and MetaRocq's guard oracle `PCUICTyping.guard_checking`, and no pass axiom (`trust_*`) and no `Admitted`. This page does not rerun the check.
- The statements of the end-to-end theorems take as input a string that is the serialization of a λ□ program (`Serialize.string_of_PAst p0` in [PipelineFirstOrder.v:215](../theories/PipelineFirstOrder.v#L215)). The parser is proved against the serializer ([PipelineParse.v](../theories/PipelineParse.v), `parse_ast_sound`, `parse_ast_canonical`). That a frontend's output is the serialization of the program the frontend meant is outside the theorems; for the Rocq frontend the serializer is the same Rocq code, for the Agda and Lean frontends it is their own.
- The theorems speak about programs whose value is first-order (`fo_sat`, [EFirstOrder.v:160](../theories/erasure/EFirstOrder.v#L160)) and relate it to the translated value (`fo_value_compile`, [EFirstOrderCorrect.v:329](../theories/erasure/EFirstOrderCorrect.v#L329)). A program returning a function is outside them.

## Rocq frontend

Main theorem. The frontend is MetaRocq's verified erasure. Peregrine composes MetaRocq's transformations into `erase_only` and `typed_erase_only` ([Erasure.v](../theories/erasure/Erasure.v), [ErasureTyped.v](../theories/erasure/ErasureTyped.v)); their types state that they relate `eval_template_program` to `EProgram.eval_eprogram EWcbvEval.default_wcbv_flags` (untyped) or `eval_typed_eprogram` (typed). The correctness obligations are those of MetaRocq's [`erase_transform`](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure-plugin/theories/ETransform.v#L198) and [`typed_erase_transform`](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure-plugin/theories/ETransform.v#L300). Peregrine has no theorem that composes the frontend with the middle-end: the middle-end theorems start from the λ□ program.

Read:

- [CoqToLambdaBox.v](../theories/CoqToLambdaBox.v): the commands `erase_untyped`/`erase_typed` quote the definition with `tmQuoteRecTransp`, erase it and print the serialization.
- [Erasure.v:76](../theories/erasure/Erasure.v#L76) and [ErasureTyped.v](../theories/erasure/ErasureTyped.v), `run_erase_only` / `run_typed_erase_only`: the precondition of erasure (a well-typed template program) is discharged with MetaRocq's axiom [`assume_that_we_only_erase_on_welltyped_programs`](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure-plugin/theories/Erasure.v#L1129). The axiom is false as a statement about all programs. Its instance for a definition that Rocq's kernel accepted is true if MetaRocq's PCUIC agrees with the kernel. The typed run also uses `PCUICSN.normalization`; this review did not trace which instance supplies it ([`fake_normalization`](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure-plugin/theories/Erasure.v#L1118) is the axiom of that class in the plugin).
- The semantics at both ends: PCUIC's weak call-by-value evaluation and λ□'s [`EWcbvEval.eval`](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/EWcbvEval.v).

Skip: MetaRocq's `erasure` and `erasure-plugin` proofs.

Outside the proof: MetaRocq's quoting (`tmQuoteRecTransp`, OCaml code of template-rocq), the correspondence between PCUIC and Rocq's kernel, the plugin in [plugin/](../plugin/) and the OCaml extraction of the frontend.

## Agda frontend

[agda2lambox](https://github.com/agda/agda2lambox) is unverified ([frontends.md](frontends.md#agda)). Its whole Haskell source is trusted. There is nothing to check against a theorem; a reviewer who wants assurance compares its output on test programs with the `eval` backend.

## Lean frontend

The Lean frontend is [lean-to-lambdabox](https://github.com/peregrine-project/lean-to-lambdabox). Peregrine does not pin it. Its correctness proofs exist only on draft branches: `ml/verification` (PR #16, model Metalean, commit `f3b934fa`) and `l4l/verification` (PR #13, model lean4lean, commit `adea293b`). The released branch `main` (commit `b50693dc`) has neither the proofs nor the verified pure path. A third stack on con-leche (draft PRs #28, #33, #34) was not examined for this page beyond the observation that its `LBEval` is a textual copy of the l4l one.

Main theorem: `EraseProof.erase_correct` on each verification branch ([ml Final.lean:51](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/proof/EraseProof/Final.lean#L51), [l4l Main.lean:30](https://github.com/peregrine-project/lean-to-lambdabox/blob/adea293b7fec400a8b8efec4a8af5a53e3be78d8/proof/EraseProof/Main.lean#L30)). It is a theorem about the pure erasure path relative to a model of Lean's type theory, with λ□ evaluation given by a Lean port of MetaRocq's `EWcbvEval.eval`.

Read: the port of `eval` (`proof/EraseProof/Target.lean`), the source evaluation relation (`SrcEval`), the statement (ml `proof/EraseProof/Statements.lean:146-163`, l4l `proof/EraseProof/Main.lean:30-38`) with the specification files it names (ml `Spec.lean`; l4l `Env.lean`, `Source/Eval.lean`, `Relation/`), the fragment test `collectDeps`, the routing in `LeanToLambdaBox/Erasure/Entry.lean`, the S-expression printer, and `doc/DIVERGENCES.md` on ml. Skip: the simulation proofs under `proof/EraseProof/` (`Simulation/`, `Core/`, the `*Ok.lean` files), which Lean and `proof/scripts/check.sh` check.

### The evaluation relation of λ□ and its two Lean ports

This section compares MetaRocq's big-step weak call-by-value evaluation of λ□, the inductive `eval` in [EWcbvEval.v:119](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/EWcbvEval.v#L119) at MetaRocq commit `51b14e4b` (the pin of peregrine-tool), with the two Lean ports used by the lean-to-lambdabox correctness proofs:

- Port 1 (Metalean stack, PR #16, branch `ml/verification`, commit `f3b934fa`): `inductive LBEval` in [proof/EraseProof/Target.lean:216](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/proof/EraseProof/Target.lean#L216).
- Port 2 (lean4lean stack, PR #13, branch `l4l/verification`, commit `adea293b`): `inductive LBEval` in [proof/EraseProof/Target.lean:187](https://github.com/peregrine-project/lean-to-lambdabox/blob/adea293b7fec400a8b8efec4a8af5a53e3be78d8/proof/EraseProof/Target.lean#L187).

The two ports are textually identical. Lines 216–296 of port 1 and lines 187–267 of port 2 (the whole inductive) agree under `diff`, as do lines 1–106 and the helper block (port 1 lines 136–215, port 2 lines 107–186). Port 1 additionally defines `lbLift` ([:109](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/proof/EraseProof/Target.lean#L109)) and `LBFixed` ([:300](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/proof/EraseProof/Target.lean#L300)). Port 2 additionally proves a nested induction principle `LBEval.ind` ([:272](https://github.com/peregrine-project/lean-to-lambdabox/blob/adea293b7fec400a8b8efec4a8af5a53e3be78d8/proof/EraseProof/Target.lean#L272)). The draft con-leche stack (PR #33, branch `cl/verification`, commit `e5f60ec4`) has its own copy at `proof/EraseProof/Target.lean:232`, whose 81 lines are identical to port 2's inductive; it is not compared further. Below, a single Lean line number refers to port 1, and port 2's line number is 29 lower for every rule.

#### 1. Flags

Rocq has a type class `WcbvFlags` with three booleans, `with_prop_case`, `with_guarded_fix` and `with_constructor_as_block` ([EWcbvEval.v:34](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/EWcbvEval.v#L34)). Both ports copy it as a structure with the same three fields ([port 1 :17](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/proof/EraseProof/Target.lean#L17), [port 2 :17](https://github.com/peregrine-project/lean-to-lambdabox/blob/adea293b7fec400a8b8efec4a8af5a53e3be78d8/proof/EraseProof/Target.lean#L17)), and `LBEval` takes the flags as a parameter; no flag is fixed inside the rules. Each flag-guarded Rocq rule keeps its guard (`fl.f = true` or `= false` in place of Rocq's `is_true` coercion or `= false`).

Both ports define `defaultFlags := ⟨true, true, false⟩` (port 1 [:23](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/proof/EraseProof/Target.lean#L23), port 2 [:23](https://github.com/peregrine-project/lean-to-lambdabox/blob/adea293b7fec400a8b8efec4a8af5a53e3be78d8/proof/EraseProof/Target.lean#L23)), which is Rocq's `default_wcbv_flags` ([EWcbvEval.v:69](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/EWcbvEval.v#L69)): prop cases on, guarded fixpoints, constructors applied (not blocks). The final theorems instantiate exactly these flags:

- Port 1: `erase_correct_statement` concludes `LBEval defaultFlags lenv tb vb` ([Statements.lean:162](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/proof/EraseProof/Statements.lean#L162)); `erase_correct` proves it ([Final.lean:51](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/proof/EraseProof/Final.lean#L51)).
- Port 2: `erase_correct` concludes `LBEval defaultFlags lenv t v'` ([Main.lean:38](https://github.com/peregrine-project/lean-to-lambdabox/blob/adea293b7fec400a8b8efec4a8af5a53e3be78d8/proof/EraseProof/Main.lean#L38)).

MetaRocq's `erase_correct` uses the same flags (`wfl := EWcbvEval.default_wcbv_flags`, [ErasureFunctionProperties.v:657](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/ErasureFunctionProperties.v#L657)), as does `erases_correct` ([ErasureCorrectness.v:51](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/ErasureCorrectness.v#L51)). At `defaultFlags` the rules `iotaBlock`, `projBlock`, `constructBlock` and `fix'` are disabled by their guards, so they are present for fidelity only.

#### 2. Rules

The Rocq relation lives in `Set` and is parameterised by a section variable `Σ` ([EWcbvEval.v:73–75](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/EWcbvEval.v#L73)); the Lean relation lives in `Prop` and takes `lenv : GlobalDeclarations`. The Lean term type `LBTerm` ([Basic.lean:96](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/LeanToLambdaBox/Basic.lean#L96) on port 1, [:90](https://github.com/peregrine-project/lean-to-lambdabox/blob/adea293b7fec400a8b8efec4a8af5a53e3be78d8/LeanToLambdaBox/Basic.lean#L90) on port 2) has no `tCoFix`, `tLazy`, `tForce`, `tEvar`, has `fvar` in place of `tVar`, and its primitive values are 63-bit integers only (`PrimTag.primInt`, port 1 Basic.lean:76–91). #### How the pure path relates to the compiled path

The two paths share one traversal. On the verification branches the erasure traversal `visitExpr` is generic in a class `Backend` that supplies the environment and the `Meta` operations ([ml Erasure.lean:222](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/LeanToLambdaBox/Erasure.lean#L222)). The production path is that traversal at the instance `Backend CoreM`; `erasePure` is the same traversal at the instance `PureM`. The instances differ in three operations, and the two outputs coincide on a program when these operations return the same answers on every call the traversal makes:

| Operation | Production (`Backend CoreM`) | Pure (`PureM`) |
|-----------|------------------------------|----------------|
| preprocessing of a body | `prepareErasure`: `_unsafe_rec` renaming, `macro_inline`, matcher inlining, `csimp` ([ml Erasure.lean:426](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/LeanToLambdaBox/Erasure.lean#L426)) | identity ([ml Pure.lean:558](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/LeanToLambdaBox/Erasure/Pure.lean#L558)) |
| declaration lookup | `declInfoCore`, through `Compiler.LCNF.getDeclInfo?`, which prefers the compiled `_unsafe_rec` definition ([ml Erasure.lean:1367](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/LeanToLambdaBox/Erasure.lean#L1367)) | `findConst decls` on the closure computed by `collectDeps`, and on ml the pre-definition from the view ([ml Pure.lean:456](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/LeanToLambdaBox/Erasure/Pure.lean#L456)) |
| type inference, `whnf`, erasability | `Meta.inferType`, `Meta.whnf` | a fuelled oracle over `decls` ([ml Pure.lean:572](https://github.com/peregrine-project/lean-to-lambdabox/blob/f3b934fab46bef707bc24fe2835a6e84d5cdecbc/LeanToLambdaBox/Erasure/Pure.lean#L572)) |

The fragment test `collectDeps` restricts the second row (definitions with an `_unsafe_rec` companion are admitted only when structurally recursive and erased through the kernel definition or the compiled pre-definition). It does not exclude programs whose bodies `macro_inline`, matcher inlining or `csimp` would change: the pure path evaluates both branches of an `if` that the production path inlines. No theorem states that the two paths agree, and `#erase` does not compare them; the corpus test described in section 4 below is the only comparison. On the verification branches `#erase` emits the pure output for every in-fragment program, so a disagreement between the paths changes how far the verified output departs from what the production path would have produced, not what is covered. For programs routed to the production path nothing is proved.

Peregrine's [OCamlBackend.v](../theories/backends/OCamlBackend.v) defines `malfunction_pipeline` (name annotation, then `compile_to_malfunction`), checks its precondition (`malfunction_check`, proved sound in `malfunction_check_sound`), and proves that output without a warning is the printed result of `malfunction_pipeline` (`extract_ocaml_verified`, [OCamlBackend.v:142](../theories/backends/OCamlBackend.v#L142)).

Two points for the reviewer. First, the `Transform.t` record [`compile_to_malfunction`](https://github.com/peregrine-project/rocq-verified-extraction/blob/f999f40ca7a2ecb52d71b5497a417ec46c5c0403/theories/Pipeline.v#L531) has `fun _ _ => True` as its target evaluation relation, so the pipeline record by itself says nothing about Malfunction evaluation; the semantic content is `compile_correct`, and no Peregrine theorem composes it with the middle-end as `peregrine_untyped_cakeml` does for CakeML. Second, the pinned rocq-verified-extraction removes the axiom `trust_coq_kernel` (commit `f999f40c`, "Remove axiom trust_coq_kernel, take the precondition as a hypothesis"); the README's statement that the glue assumes it describes the earlier pin.

Read: `compile_correct` and its hypotheses (`supported`, `malfunction_env_prop`), `SemanticsSpec.v` (the Malfunction semantics, 849 lines), [OCamlBackend.v](../theories/backends/OCamlBackend.v), [ExtractionCheck.v](../theories/backends/ExtractionCheck.v) (placeholder bodies for axioms and remapped constants).

Outside the proof: the S-expression printer of Malfunction (`Serialize_module`), the `malfunction` tool and the OCaml compiler, the agreement of `SemanticsSpec` with them, and remapped constants.

## CakeML

Main theorems: [`peregrine_untyped_cakeml`](../theories/PipelineCakeML.v#L155) and [`peregrine_typed_cakeml`](../theories/PipelineCakeML.v#L184). They compose the middle-end theorems with cakeml-backend's compiler correctness (`cakeml_correct_named_vrel` in `theories/Backend/CompileCorrect.v` of cakeml-backend): if the input evaluates to a first-order value and Peregrine produces the `.cml` file without a warning, the main expression of the file evaluates, in a Rocq formalization of CakeML's big-step semantics and after the file's datatype and `val` declarations, to a value related to the λ□ value. These are the only end-to-end theorems in Peregrine that reach a target-language semantics.

Read: the statements and [`cakeml_output_correct`](../theories/PipelineCakeML.v#L98), [CakeMLBackend.v](../theories/backends/CakeMLBackend.v) (`cakeml_check`, `extract_cakeml_verified`), and the Rocq formalization of CakeML's semantics in cakeml-backend (`theories/CakeML/ast.v`, `bigstep.v`, `semanticPrimitives.v`, `namespace.v`, `functions.v`) together with the declaration model in `theories/Backend/CompileCorrect.v`. The following subsection compares it with CakeML's HOL4 semantics.

Skip: the proofs in cakeml-backend's `CompileCorrect.v` and `PipelineCorrect.v`, `theories/CakeML/proofs/`, and Peregrine's `PipelineCakeML.v` proofs.

Outside the proof: the S-expression printer (`Serialize_module`), CakeML's S-expression parser, its type inference (skipped with `--skip_type_inference=true`) and its compiler; the faithfulness of the Rocq formalization to HOL4, which no mechanised proof establishes.

### Rocq semantics against HOL4 semantics

#### What the theorem states on the CakeML side

[`peregrine_untyped_cakeml`][p-untyped] and [`peregrine_typed_cakeml`][p-typed] conclude [`cakeml_output_correct`][p-occ]: the printed output is the serialisation of `compile_cakeml (env, t)` ([CakeMLBackend.v:136][p-cc]), and for every `n0`, `env0`, `genv` with [`eval_program_decls`][r-epd] `n0 env0 decls genv`, the main expression satisfies [`bigstep.evaluate`][r-eval] `genv main (Rval w)` with `w` related by [`vrel`][r-vrel] to the λ□ value. [`cakeml_output_correct_fo`][p-fo] specialises `w` to [`compile_value`][r-cv] when the value is a constructor tree. The CakeML-side definitions involved are therefore `bigstep.evaluate` (with `evaluate_list` and `evaluate_match`), the value and environment types of [namespace.v][r-ns], the helpers of [semanticPrimitives.v][r-sp], and the declaration model `eval_dtypes`/`eval_decls` in [CompileCorrect.v:1059–1093][r-decls]; the file header lists the S-expression printer, the CakeML parser and the CakeML compiler as trusted ([PipelineCakeML.v:22–31][p-trusted]).

- Rocq side: peregrine-project/cakeml-backend at `dae906dee07e3e0c7bc6de3229a3d7ea66a645dd` (2026-11-19), the commit pinned in `rocq-peregrine.opam`. Peregrine at peregrine-tool `e526773e4ae7566339ab6de3e0a372d00359749f`.

[bigstep.v:12][r-hdr] cites `bigStepScript.sml#L68` on `master`; line 68 is `Inductive evaluate:` at e1650fc ([link][ho-eval]), not at current master (line 20). Two further details match e1650fc and not master: the `opClass op FunApp` premise of the application rule ([e1650fc bigStep:144][ho-app]) and the two-field `TypeStamp conN num` ([e1650fc semanticPrimitives:17][ho-stamp]). No file header mentions Lem; the Rocq files are a hand-written restriction of the HOL definitions (names such as `ALOOKUP`, `ALL_DISTINCT`, `Bind` are kept).

#### Points for the reviewer

1. Each Rocq rule in `bigstep.v` is an instance of a HOL rule with ck = F and the state unchanged. This was checked by reading the clauses cited above; no mechanised embedding of the Rocq relation into the HOL one exists in either repository.
2. The Rocq semantics has no error results apart from `Rraise`, so a type error or a timeout shows up as the absence of a derivation. A positive Rocq result transfers to HOL by item 1, and HOL determinism ([determScript:15][h-det]) then makes it the only HOL result.
3. `cakeml_output_correct` quantifies over runs of the declarations and does not assert that a run exists ([CompileCorrect.v:1091][r-epd]). A search of cakeml-backend and peregrine-tool for an existence lemma found none. If a `Dlet` raised or diverged in CakeML, the statement would hold vacuously.
4. Master's `check_exp_constructors` on `Dlet` requires that every emitted `Con` has the declared arity. The backend precondition sets `cstr_as_blocks := true` and `has_cstr_params := false` ([Pipeline.v:160–168][r-flags]), and under these flags MetaRocq's `wellformed` (at the pinned commit 51b14e4b, [EWellformed.v:147–151][m-wf]) requires exactly that arity. This review did not trace that the named flags used by `good_for_extraction` keep this clause.
5. The value in the first-order theorem uses two-field stamps; comparing it with master requires adding each constructor's position to its stamp.
6. The emitted program binds the value of `main` and prints nothing ([Serialize.v:129–133][r-sm]); the theorem is about that value, not about observable output.

Not verified:
- That `cake` at the pinned master parses the emitted S-expressions as intended (for example, that the bare name in `Dlet (unk unk) "x" e` is read as `Pvar "x"`, and that the atom `Strlit` is read as a string literal). The S-expression parser was not read.
- That the top-level state in which `cake` runs a program has `eval_state = NONE`, which `functional_evaluate` requires.
- That the CakeML basis environment, which plays the role of `env0`, cannot capture an emitted name. Emitted constants and constructors contain dots (CompileCorrect.v:89–96 proves this for constants), but the basis was not inspected.
- `smallstep.v` and its equivalence proof (`proofs/equivalence_proofs.v`) were not compared with HOL's `smallStepScript.sml`; the theorem does not use them.

## Rust

Main theorem: the typed middle-end, [`peregrine_typed_typed_fo`](../theories/PipelineFirstOrder.v#L338), which ends at the λ□ᵀ program handed to the printer. Before it, typed erasure of Rocq programs is MetaRocq's (`erasure/theories/Typed/`: [ErasureCorrectness.v](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/Typed/ErasureCorrectness.v), [OptimizeCorrectness.v](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/Typed/OptimizeCorrectness.v) for dead-argument removal, `dearg_correct` at line 4401, and [ExtractionCorrectness.v](https://github.com/MetaRocq/metarocq/blob/51b14e4bb5f4580f00f60208ff8dbf31f3ad6f56/erasure/theories/Typed/ExtractionCorrectness.v), `extract_correct` at line 530). The repository peregrine-project/rocq-typed-extraction holds the printers only; it has no proofs at the pin.

The printer, in rocq-typed-extraction at `74dcbc96`:

- [rust/theories/RustExtract.v](https://github.com/peregrine-project/rocq-typed-extraction/blob/74dcbc960a8d4fa04496b84d6447611159bd6c70/rust/theories/RustExtract.v): types (`print_type`, line 226), terms ([`print_term`, line 441](https://github.com/peregrine-project/rocq-typed-extraction/blob/74dcbc960a8d4fa04496b84d6447611159bd6c70/rust/theories/RustExtract.v#L441)), constants ([`print_constant`, line 602](https://github.com/peregrine-project/rocq-typed-extraction/blob/74dcbc960a8d4fa04496b84d6447611159bd6c70/rust/theories/RustExtract.v#L602)), inductives (`print_mutual_inductive_body`, line 715), the program ([`print_program`, line 814](https://github.com/peregrine-project/rocq-typed-extraction/blob/74dcbc960a8d4fa04496b84d6447611159bd6c70/rust/theories/RustExtract.v#L814)).
- [rust/theories/Printing.v](https://github.com/peregrine-project/rocq-typed-extraction/blob/74dcbc960a8d4fa04496b84d6447611159bd6c70/rust/theories/Printing.v): the remapping record.

Peregrine's side:

- [RustBackend.v](../theories/backends/RustBackend.v): configuration, the preamble (`rust_top_preamble`, `rust_program_preamble`), remaps (`mk_remaps`), `eta_remapped_bodies`, `extract_rust`.

- Coherence of the numeric remaps, proved for models over `Z`: [RustMixedCoherence.v](../theories/backends/RustMixedCoherence.v) (the `i64` operations of `mixed` agree with the `nat` operations when arguments and result fit in `i64`); for `hybrid`, [HybridRuntime.v](../theories/backends/HybridRuntime.v) writes the arithmetic in Rocq over the primitives of [HybridPrims.v](../theories/backends/HybridPrims.v) and proves each operation (`add_spec` to `compare_spec`, the fast paths `add_fast_ok` and following); the Rust printed from it is generated into [HybridRuntimeGen.v](../theories/backends/HybridRuntimeGen.v); [RustHybridCoherence.v](../theories/backends/RustHybridCoherence.v) models the hand-written kernel, comparisons and eliminators of `RustHybridRemaps.v` and proves them against `Z`. These theorems are about models: each primitive of `HybridPrims.v` is trusted to compute its Rocq body, and the hand-written Rust strings are trusted to compute their models.

Read: the printer files above, `RustBackend.v`, the remap files (the Rust strings), `HybridPrims.v` (the primitive models), and the statements of the coherence files.

Skip: the proofs in `HybridRuntime.v`, `RustHybridCoherence.v`, `RustMixedCoherence.v`, MetaRocq's typed erasure proofs.

Outside the proof: the printer; untyped input, typed by Hindley-Milner inference without a correctness theorem; the Rust strings of the remaps and their agreement with the models; the crates `bumpalo` and `rug` (GMP); `rustc`. The `i64` and `mixed` representations do not check overflow (see [backends.md](backends.md#numeric-representations)).

## Debug backends: eval and ast

`ast` ([ASTBackend.v](../theories/backends/ASTBackend.v)) prints the program after the middle-end with the serializer whose round trip with the parser is proved ([theories/serialization/](../theories/serialization/), [PipelineParse.v](../theories/PipelineParse.v)).

`eval` ([EvalBackend.v](../theories/backends/EvalBackend.v)) compiles the program with CertiRocq's λ□ to LambdaANF pipeline and runs the fuel-bounded interpreter of [EvalBox.v](../theories/EvalBox.v) (fuel `2^18`). `EvalBox.v` contains no theorem; the interpreter is trusted, and its result is evidence, not proof, about the program.
